## 1. 공공 API

### 1-1. 상하행 코드가 문서와 반대 (`2cfa5cc`)

**문제** — 역 상세의 첫차·막차 카드가 방향을 바꿔 보여주고 있었다. 강남구청 "청담 방면"(상행)
첫차가 05:48로 나왔지만 실제 상행 첫차는 05:33이고, 05:48은 반대편 "학동 방면"의 값이다.

**발견 경위** — 시간표 시트에 방향 전환 탭을 넣고 기기에서 전환해 보니, 상행 탭에
하행 종착역(석남·온수)이 나왔다.

**원인** — `SearchSTNTimeTableByFRCodeService`의 `upDownCode`를 이름 그대로 1=상행으로
넣고 있었다. 실제로는 1이 하행이다. 3개 노선에서 교차 확인했다.

| 역 | `upDownCode=1` | `upDownCode=2` |
|---|---|---|
| 7호선 강남구청 | 석남 127 · 온수 71 (남) | 도봉산 113 · 장암 83 (북) |
| 4호선 사당 | 오이도 109 (남) | 불암산 146 · 진접 77 (북) |
| 1호선 남영 | 인천 108 · 서동탄 42 (남) | 광운대 70 · 청량리 44 (북) |

**조치** — `StationRepository.getStationTimeTable()`에서 `up`/`down`에 넘기는 코드를 맞바꿨다.
실시간 도착의 방향 판정은 응답의 `updnLine` 문자열을 쓰므로 영향이 없고, TAGO 폴백은
`"U"`/`"D"`를 따로 쓴다. 영향 범위는 시간표 두 곳뿐이다.

관련 파일: `repository/StationRepository.kt`, `api/SubwayApiService.kt`

### 1-2. `LEFTTIME`에 `00:00:00` 자리표시가 섞여 온다 (`549af31`)

**문제** — 시간표에 "0시" 섹션이 생기고 분이 전부 `00`인 줄이 수십 개 나올 수 있었다.

**발견 경위** — 상하행 코드 수정을 검증하려고 4호선 사당의 첫차·막차를 API와 대조하다가
상행 첫차가 `00:00`으로 나오는 것을 발견했다.

**원인** — 사당 상행 **237행 중 110행(46%)**의 `LEFTTIME`이 `00:00:00`이었다. 이 API는
자정을 넘긴 열차를 `24:08`·`25:02`로 이어 쓰므로 `00:`으로 시작하는 값은 시각이 아니라
빈 자리표시다. 7호선 강남구청(200행)과 9호선 고속터미널(243행)에는 이 행이 없어
역·노선마다 다르다.

**조치** — 시간표 시트에서 `00:`으로 시작하는 행을 거른다. 사당 상행 첫차가 `05:50`으로
정상화된다.

관련 파일: `ui/screen/station/StationTimetableSheet.kt`의 `isRealDeparture()`

### 1-3. `ordkey`는 도착 시간 순이 아니다 (`57d4fef`)

**문제** — 수원역 하행에 "5분 / 24분 / 5분"처럼 순서 없이 나왔다.

**발견 경위** — 화면에서 시간이 뒤섞여 보인다는 지적을 받고 원시 응답을 수집해 대조했다.

**원인** — 서울 API는 도착 시간이 아니라 **(급행 여부 → 순번)** 순으로 내려준다.
`ordkey` 자릿수를 해독하면 구조가 드러난다.

```
1 1 001 인천 0
│ │  │   │   └ 급행 여부 (0=일반, 1=급행)
│ │  │   └───── 종착역
│ │  └───────── 남은 역 수
│ └──────────── 그 계통 안에서의 순번
└────────────── 0=상행, 1=하행
```

검증: 6583은 `arvlMsg3=매교`(1역 전)이고 `001`, 6405는 `[12]번째 전역`이고 `012`,
6407은 `[16]번째`이고 `016`으로 전부 일치했다.

일반 계통과 급행 계통이 번갈아 끼어들어 수원 하행이 1역 → 12역 → 1역 → 16역 순으로
나열됐다. 앱은 필터만 하고 정렬하지 않았다.

**조치** — 화면에 표시할 추정 분을 그대로 정렬 키로 쓴다. 표시값이 반드시 단조 증가한다.
같은 분이면 남은 역 수가 적은 쪽이 앞선다. 규칙을 `util/ArrivalOrdering.kt` 한 곳에 두고
역 상세·홈·위젯이 공유한다.

관련 파일: `util/ArrivalOrdering.kt`, `test/util/ArrivalOrderingTest.kt`

### 1-4. `recptnDt`를 보지 않아 떠난 열차를 계속 보여줬다 (`57d4fef`)

**문제** — 이미 떠난 열차가 "도착"·"진입" 상태로 목록에 남았다.

**발견 경위** — 수원역 상행이 "진입 / 도착 / 도착"으로 세 대가 모두 곧 도착으로 표시됐다.

**원인** — 급행 계통의 응답이 일반보다 일관되게 뒤처져 내려온다. 수원역 실측에서
일반 행은 0.0~1.4분, 급행 행은 4.6~5.0분 전 데이터였다. 한 번은 **16.8분 전** 데이터가
"진입"으로 표시됐다. 앱은 `recptnDt`를 DTO에 받지도 않았다.

**조치** — `recptnDt`를 DTO에 추가하고, 상태가 "도착"·"진입"인데 3분 이상 지난 행을 거른다.
임계를 90초로 잡으면 급행이 상시 사라져 "이 역에 급행이 안 온다"로 오해된다.

관련 파일: `dto/RealtimeArrival.kt`, `util/ArrivalOrdering.kt`

### 1-5. `"전역 도착"`을 현재 역 도착으로 오인 (`abab245`)

**문제** — 인접한 두 역에서 같은 열차의 도착 시간이 뒤집혀 보였다. 수원 상행 11분,
다음 역인 매교 상행 5분.

**발견 경위** — 홈 화면에서 수원과 매교의 상행 시간이 진행 방향과 반대인 것을 지적받고,
두 역과 수원시청까지 세 역을 같은 시점에 수집해 대조했다.

**원인** — `getFormattedMessage()`가 `endsWith("도착")`을 먼저 검사해 `"전역 도착"`을
`"도착"`으로 바꿨다. 이전 역에 도착했다는 뜻인데 현재 역 도착과 구분되지 않았다.
수집 표본 **62건 중 12건(19%)**이 이 경우였다.

여기에 1-4의 3분 필터가 겹쳤다. 수원에서 가까운 열차들이 `"전역 도착"`이라 "도착" 라벨을
달았고 낡은 데이터라 걸러졌다. 그 결과 훨씬 먼 열차가 첫 줄로 올라왔다. 매교에서는 같은
열차가 `"[2]번째 전역"`으로 와서 그대로 남았다.

**조치** — `startsWith("전역")` 검사를 `endsWith` 앞으로 옮겼다. 이 한 곳으로 셋이 함께
해결된다 — 표시 정확도, 필터의 대칭성, 정렬 키와 표시값의 일치.

검증(세 역 동시 수집): 상행 열차 6582가 수원 도착 / 매교 3분 / 수원시청 5분,
하행 열차 6177이 수원시청 5분 / 매교 8분 / 수원 11분으로 진행 방향을 따라 단조 증가했다.

관련 파일: `dto/RealtimeArrival.kt`, `test/dto/RealtimeArrivalTest.kt`

### 1-6. `"전역 출발"`이 떠난 열차로 걸러졌다 (`abab245`)

**문제** — 가장 가까운 열차가 목록에서 사라졌다.

**발견 경위** — 1-5 수정에 테스트를 붙이다 `"전역 출발"`의 기대값을 `"출발"`로 썼는데
실패했고, 확인해 보니 기대값 쪽이 틀렸다.

**원인** — `"전역 출발"`은 *이전 역을 떠났다* = 이쪽으로 오고 있다는 뜻이다. 그런데
`endsWith("출발")`로 잡혀 `"출발"`이 되었고, `ArrivalOrdering`이 떠난 열차로 보고 제외했다.
총신대입구(이수) 응답 8건 중 1건이 이 형태였다.

**조치** — 1-5의 `startsWith("전역")` 이동이 이 경우도 함께 처리한다. 회귀 방지 테스트를
따로 두었다.

### 1-7. 역명의 괄호 부제 때문에 역명이 상태로 표시됐다 (`092b8b4`)

**문제** — 홈 화면 총신대입구(이수) 행의 상태 칩에 `"총신대입구"`라는 역명이 찍혔다.
정상이라면 "도착" 또는 "진입"이어야 한다.

**발견 경위** — DB에 직접 넣어 확인하던 긴 역명 표본에서 드러났다.

**원인** — `arvlMsg2`를 `substringBefore("(")`로 잘라 꼬리의 "(다음 역)"을 떼고 있었다.
역명 자체에 괄호가 있으면 역명이 먼저 잘린다.

```
"총신대입구(이수) 도착"  →  "총신대입구"
```

잘린 문자열은 "도착"·"진입"·"출발" 어디에도 걸리지 않아 마지막 분기로 빠져 역명이 그대로
반환됐다. 홈 화면은 "N분"이 아닌 문자열을 상태 칩에 넣으므로 빨간 칩에 역명이 들어갔다.

영향 범위는 서울 지하철 **655개 역 중 괄호 부제를 가진 67개(10.2%)** 전부다.
총신대입구(이수)·서울대입구(관악구청)·교대(법원.검찰청)·잠실(송파구청)·왕십리(성동구청)·
청량리(서울시립대입구)·이촌(국립중앙박물관) 등이 해당한다.

**조치** — 꼬리 괄호만 떼는 정규식으로 바꿨다. greedy라서 `"6분 후 (상도(중앙대앞))"`처럼
꼬리 괄호 안에 또 괄호가 있는 경우도 통째로 걷힌다.

이 결함은 최초 코드부터 있었다. 상태 칩(`b1d218e`)이 들어오기 전에는 역명이 평범한 글자로
나와 묻혔을 뿐이다.

### 1-8. `EXPRESS_YN`이 `"Y"`가 아니라 `"D"`/`"G"` (`aa763ad`)

**문제** — 급행 표식이 한 번도 화면에 나온 적이 없었다.

**발견 경위** — 시간표 시트를 재설계하며 실데이터 분포를 확인하다 `EXPRESS_YN` 값이
`"Y"`가 아닌 것을 발견했다.

**원인** — `isExpressTrain()`이 `express == "Y"`를 보고 있었다. 서울 API의 실제 값은
`"D"`와 `"G"`뿐이라 항상 false였다.

| 역 | D | G | 급행 정차 |
|---|---|---|---|
| 9호선 고속터미널 | 118 | 125 | 정차 |
| 9호선 사평 | 0 | 125 | 미정차 |
| 7호선 강남구청 | 0 | 200 | 급행 없음 |

급행 미정차역에 D가 하나도 없고 정차역에만 있어 `D`가 급행이다.

**조치** — `"D"`를 급행으로 판정하되 TAGO 폴백이 주는 `"Y"`도 함께 받는다. 급행이 다니는
역까지 가야 화면에서 확인할 수 있어 판정 자체를 단위 테스트로 고정했다.

관련 파일: `api/ExtendedStationDto.kt`, `test/api/TimeTableScheduleTest.kt`

## 2. 환경·구조

### 2-1. `recptnDt` 비교가 기기 타임존에 의존했다 (`43e2865`)

**문제** — CI에서 테스트 1건이 실패했다. 로컬에서는 통과했다.

**발견 경위** — 위젯 정합 작업을 push한 뒤 GitHub Actions가 실패했다.

**원인** — 1-4의 떠난 열차 판정이 `recptnDt`를 기기 타임존의 `LocalDateTime`으로 읽고
있었다. 이 값에는 타임존 표기가 없고 서울 열린데이터 광장이 주는 것이라 항상 KST다.
로컬(KST)에서는 우연히 맞아떨어졌고, CI(UTC)에서는 9시간 어긋나 필터가 동작하지 않았다.
기기가 해외에 있어도 같은 문제가 생긴다.

**조치** — 파싱한 시각을 `Asia/Seoul`로 고정해 `Instant`로 바꾸고 `clock.instant()`와
비교한다. 양쪽 모두 절대 시각이라 실행 환경과 무관해진다.

관련 파일: `util/ArrivalOrdering.kt`

### 2-2. Room 인스턴스가 이중으로 생성됐다 (`d2abba8`)

**문제** — 같은 DB 파일에 `RoomDatabase` 인스턴스가 두 개 만들어지고 있었다.

**발견 경위** — 위젯 갱신 Worker만 Hilt 밖에 있어 의존성을 직접 만들어 쓰는 것을 정리하다
드러났다.

**원인** — `AppDatabase`가 `@Volatile INSTANCE` + `synchronized` 자체 싱글턴을 갖고 있었고,
동시에 Hilt `AppModule`이 별도로 인스턴스를 만들고 있었다. 화면은 Hilt 쪽을,
`ArrivalWidgetUpdateWorker`는 `AppDatabase.getDatabase(context)` 쪽을 썼다.

**조치** — Worker를 `@HiltWorker` + `@AssistedInject`로 전환해 DAO를 주입받게 하고,
`AppDatabase`의 자체 싱글턴을 제거했다. DB 생성 경로가 Hilt 한 곳으로 정리됐다.
같은 커밋에서 Worker의 Retrofit 수동 생성과 `BuildConfig` 직접 참조도 걷어냈다.

관련 파일: `db/AppDatabase.kt`, `di/AppModule.kt`, `widget/ArrivalWidgetUpdateWorker.kt`

### 2-3. 근처 역이 비면 위치를 읽지 않는 조건 (`0dd5b21`)

**문제** — 근처 역 지도가 기본 좌표(0, 0)에 머물렀다.

**발견 경위** — 위치 조회 계층을 정리하며 세 화면의 코드를 대조하다 조건문이 뒤엉킨 것을
발견했다.

**원인** — 두 가지가 겹쳤다. 첫째, `HomeScreen`·`MapScreen`·`StationScreen` 세 곳이
`FusedLocationProviderClient`를 UI에서 직접 만들어 `lastLocation`만 호출했는데,
캐시된 위치가 없으면 null을 반환하고 폴백이 없어 조용히 실패했다. 둘째, 카메라 이동
조건에 `nearbyStations.isNotEmpty()` 게이트가 있어 **역 목록이 비어 있으면 위치를 읽는
코드 자체가 실행되지 않았다.** 위치가 없어 역 목록이 비고, 역 목록이 비어 위치를 읽지 않는
순환이었다.

**조치** — `LocationRepository.getCurrentLocation()`으로 일원화하고, 캐시된 위치가 없으면
`requestLocationUpdates()`의 첫 fix를 5초까지 기다린다. 게이트 조건을 제거하고,
`LocationState(Loading/Available/Unavailable)`를 상태로 노출해 실패를 화면에 드러낸다.

관련 파일: `repository/LocationRepository.kt`, `viewModel/LocationState.kt`

### 2-4. API 키가 소스에 하드코딩돼 있었다 (`59c8bbd`, `3ae78a6`)

**문제** — 공공 API 키 4종이 Retrofit 어노테이션 경로와 Repository 지역변수에 박혀 있었고,
Google Maps 키는 `AndroidManifest`에 평문으로 있었다.

**발견 경위** — 저장소를 공개하기 전 점검.

**원인** — 초기 구현이 키를 상수로 두고 시작했다.

**조치** — 두 단계로 나눠 처리했다. 먼저 공공 API 키를 `local.properties` →
`buildConfigField` → `BuildConfig` 경로로 옮겼다. 키가 URL 경로 중간에 들어가는
엔드포인트가 있어 OkHttp 인터셉터 대신 `@Path`/`@Query` 파라미터화를 택했다.

Maps 키는 지도 SDK가 매니페스트 `meta-data`에서 직접 읽으므로 `BuildConfig`를 쓸 수 없어
`manifestPlaceholders`로 주입했다. 노출 시 실제 과금이 발생할 수 있어 우선 처리했다.

이후 `@Named String` 프로바이더 4개를 `ApiKeys` 데이터 클래스 하나로 합쳤다. Repository는
키 문자열 대신 `ApiKeys`를 주입받으므로 인증 정보가 데이터 계층 시그니처에 노출되지 않는다.
`BuildConfig`를 참조하는 코드는 `AppModule` 하나뿐이다.

관련 파일: `di/ApiKeys.kt`, `di/AppModule.kt`, `app/build.gradle.kts`, `local.properties.example`

## 4. 알고 있으나 다루지 않은 것

이번 작업 범위 밖이라 남겨 둔 것들이다. 발견 경위와 현재 코드 상태만 적는다.

### 4-1. 일일 API 한도 소진이 화면에 드러나지 않는다

실시간 도착 API는 일일 1,000건 제한이 있다. `StationRepository`는 연속 3회
실패하면 `isApiLocked`를 세워 이후 호출을 건너뛴다.

```kotlin
private var isApiLocked = false
private var retryCount = 0
private val MAX_RETRIES = 3
```

이 값이 `private`이고 Repository 밖으로 나가지 않는다. 잠긴 뒤에는 캐시된 값이
있으면 그것을, 없으면 빈 리스트를 반환한다. 화면은 "도착 정보 없음"만 보여주므로
한도를 다 썼는지, 네트워크가 끊겼는지, 정말 열차가 없는지 구분할 수 없다.

관련 파일: `repository/StationRepository.kt`

### 4-2. 마지막 조회 결과를 캐시하지 않는다

실시간 도착은 역 이름별 10초 인메모리 캐시(`arrivalCache`)만 있다. 프로세스가
죽으면 사라지고 영속 저장이 없다. Room에는 즐겨찾기·최근검색·알람만 있다.
비행기 모드에서 앱을 열면 즐겨찾기 목록은 나오지만 도착 시간은 전부 비어 있다.

### 4-3. 홈에 네트워크 실패 표시가 없다

오류를 화면 상태로 올리는 곳은 `StationUiState.errorMessage` 하나이고, 채워지는
경우도 역 상세의 첫차·막차 조회가 상·하행 모두 실패했을 때뿐이다.
`MainViewModel`에는 오류 상태가 없다. 홈에서 조회가 실패하면 조용히 빈 값이 된다.

Repository의 반환 규약이 "실패 시 빈 값"이라 실패와 빈 결과가 호출부에서
구분되지 않는 것이 근본 원인이다. 규약을 바꾸면 영향 범위가 넓어 이번에는 두었다.

### 4-4. Compose UI 테스트가 없다

단위 테스트 38건은 전부 JVM에서 도는 것이고 `app/src/androidTest` 소스셋 자체가
없다. 화면 상태 전이(빈 상태, 방향 전환 탭, 즐겨찾기 토글의 UI 반영)는
검증되지 않았다.

### 4-5. 위젯이 크기와 무관하게 3개 고정이다

`ArrivalWidget.MAX_FAVORITES = 3`이고 Glance `SizeMode.Responsive`를 쓰지 않는다.
`arrival_widget_info.xml`이 `resizeMode="horizontal|vertical"`이라 사용자가 크기를
줄일 수 있는데, 2×2로 줄여도 3개를 그리려 해서 잘린다.

관련 파일: `widget/ArrivalWidget.kt`, `res/xml/arrival_widget_info.xml`

### 4-6. 도착 알림이 폴링 구조라 생기는 한계

지금 구조는 이렇다.

```
예상 도착 시각 - 임계값 - 60초 후에 워커를 깨운다      SubwayAlarmManager.kt:46
깨어나면 실시간 도착 API를 다시 조회한다
남은 시간 <= 임계값이면 알림을 띄우고 끝낸다           SubwayAlarmWorker.kt:61
아니면 남은 시간에 따라 30초 / 1분 / 2분 뒤 다시 조회   SubwayAlarmWorker.kt:70-75
최대 1시간까지 반복한다                                SubwayAlarmWorker.kt:31
```

폴링을 택한 이유는 두 가지다. 구현이 단순하고, 도착 시각이 계속 바뀌는 데이터를
자연스럽게 따라간다. 예약 시점의 "15분 후"가 실제로는 18분이 되어도 폴링이
그 변화를 그대로 반영한다.

대가는 아래 네 가지다.

**WorkManager의 비포그라운드 실행 한도는 약 10분인데 워커는 1시간을 감시하려 한다.**
한도에 닿으면 시스템이 워커를 중단하고 WorkManager가 다시 실행하는데, `doWork()`가
처음부터 도므로 `startTime`이 초기화된다(`SubwayAlarmWorker.kt:30`). 1시간 상한이
의도대로 동작하지 않는다. 실측한 워커는 2분 31초 만에 끝나 한도에 닿지 않았고,
10분을 넘겨 감시해야 하는 상황은 재현하지 못했다.

**Doze와 앱 대기 버킷에 대응하지 않는다.** `setExpedited`, 포그라운드 서비스,
`setRequiresDeviceIdle` 중 아무것도 쓰지 않는다. 화면을 끄고 오래 두면 폴링 간격이
늘어지거나 워커가 유지 구간까지 밀린다. 장시간 방치가 필요해 확인하지 못했다.

**알람 1건이 최대 120회 API를 호출한다.** 30초 간격으로 1시간을 채우는 경우다.
실시간 도착 API의 일일 한도가 1,000건이므로 12%에 해당한다. `StationRepository`의
캐시는 10초라 30초 폴링을 걸러 주지 못한다. 실측에서는 2분 31초 동안 약 6회였다.

**폴링 간격이 30초라 "1분 전"은 최대 30초 어긋난다.** 임계값을 넘긴 순간이 아니라
다음 폴링 시점에 알림이 나간다.

대안은 **예상 시각에 한 번만 깨어나 확인하고, 어긋났으면 다시 예약하는** 구조다.
깨어나서 남은 시간이 임계값 안이면 알림을 띄우고, 아직 멀면 새로 계산한 시각으로
`OneTimeWorkRequest`를 다시 건다. 워커가 몇 초만 살므로 10분 한도와 무관해지고,
호출 수도 알람 1건당 두어 번으로 줄며, 한 번만 깨우면 되므로 `setExpedited`나
`AlarmManager.setExactAndAllowWhileIdle`로 Doze를 넘길 여지가 생긴다.

대신 재예약 로직이 필요하고, 깨어난 사이에 도착 시각이 크게 당겨지면 놓칠 수 있다.
그 경우를 막으려면 여유를 두고 여러 번 깨워야 해서 결국 성긴 폴링에 가까워진다.
이번에는 구조를 바꾸지 않고 두었다.

### 4-7. 알림 권한이 없으면 예약이 조용히 사라진다

워커가 알림을 띄우기 직전에 권한을 확인하는데, 권한이 없으면 그냥 돌아간다.

```kotlin
private fun showNotification(...) {
    if (!notificationHelper.areNotificationsEnabled()) {
        return
    }
    ...
}
```

호출부는 반환값을 보지 않고 그대로 `deactivateAlarm`을 부른 뒤 성공으로 끝낸다
(`SubwayAlarmWorker.kt:64-66`). 예약할 때는 권한을 확인하지만, 예약한 뒤 사용자가
설정에서 알림을 끄면 예약이 흔적 없이 없어진다.

관련 파일: `alarm/SubwayAlarmWorker.kt:92-96`

### 4-8. 실시간 API 잠금이 풀리지 않는다

`StationRepository`는 연속 3회 실패하면 `isApiLocked = true`로 호출을 멈추는데,
이 값을 `false`로 되돌리는 코드가 없다. 대입은 초기화(37행)와 설정(79행) 두 곳뿐이다.
`@Singleton`이므로 프로세스가 죽을 때까지 잠긴 채로 남는다.

알람 워커가 그동안 도는 중이면 낡은 캐시만 보게 된다. 캐시가 비어 있으면 대상 열차를
찾지 못해 폴링만 하다 끝나고, 캐시가 남아 있으면 이미 지나간 열차 데이터로 알림을
띄울 수 있다. 4-1과 같은 코드에서 나오는 별개의 문제다.

관련 파일: `repository/StationRepository.kt:37,47,79`

### 4-9. 발화한 알람 행이 삭제되지 않는다

알람은 발화하거나 취소될 때 `isActive = 0`으로 내려갈 뿐 지워지지 않는다
(`SubwayAlarmEntity.kt:30`). `deleteAlarm` 쿼리는 정의만 되어 있고 호출하는 곳이 없다
(`SubwayAlarmEntity.kt:33-34`). 목록 조회가 `isActive = 1`만 보므로 화면에는 영향이
없지만, 행은 계속 쌓인다. 검증에 쓴 기기에는 9행이 남아 있다.

### 4-10. 알람 전용 테스트가 없다

`SubwayAlarmManager`, `SubwayAlarmWorker`, `NotificationHelper` 어느 것도 테스트가
없다. `StationViewModelTest`가 이들을 mockk로 대체할 뿐이다. 예약 지연 시간 계산,
폴링 종료 조건, 알림 발화 조건은 전부 기기에서 손으로 확인했다.

`RealtimeArrival.secondsUntilArrival()`은 순수 함수라 단위 테스트가 있다.

### 4-11. 알림 탭에서 같은 역·같은 종착역의 두 열차가 구분되지 않는다

알림 탭의 한 줄은 역 이름과 아래 문장으로만 이루어진다.

```kotlin
text = "${alarm.destination}행 · 도착 ${alarm.alarmTimeThreshold / 60}분 전 알림"
```

열차를 구분하는 값이 들어가지 않는다. 기기에서 수원역에 두 건을 예약해 확인한
결과는 아래와 같았다.

```
수원역   인천행 · 도착 5분 전 알림
수원역   왕십리행 · 도착 5분 전 알림
```

종착역이 달라 구분됐지만, 같은 방향의 두 열차는 종착역이 같은 경우가 많다.
2호선 내선은 연속한 두 대가 모두 "성수행"이다. 그때는 예고 시간까지 같으면 두 줄이
완전히 같아진다.

구분하려면 예약 당시의 도착 예정 시각을 저장해 보여줘야 하는데, `SubwayAlarmEntity`에
컬럼이 없어 Room 마이그레이션이 생긴다. 이번 범위에서는 두었다.

관련 파일: `ui/screen/AlarmScreen.kt:117`, `db/SubwayAlarmEntity.kt`

### 4-12. 도착 카드가 3대까지만 그려 그 뒤 열차는 예약할 수 없다

알람을 열차별로 걸 수 있게 됐지만, 카드가 `arrivals.take(3)`으로 잘라 그린다
(`StationArrivalDirectionCard.kt:105`). 실시간 도착 API가 방향당 2건을 주는 경우가
많아 실사용에서 드러나지는 않지만, 더 뒤 열차에 알림을 걸 방법은 없다.
